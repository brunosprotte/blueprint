## 1. Objetivo

Transformar tudo que o servidor autoritativo conhece — corpus do método, artefatos de
repo, commits, reviews e dúvidas — em **chunks pesquisáveis**, e expor duas rotas:
busca (`GET /api/knowledge`) e dossiê (`GET /api/knowledge/dossier/{demand_id}`).

A busca é **BM25 em duas etapas**: candidatos via Postgres FTS, rerank em Python puro
com a mesma fórmula do `tools/retrieve.py`. Sem embeddings, sem Voyage, sem modelo local.

**Critério de sucesso da fase:** `GET /api/knowledge?q=…` devolve hits ranqueados por
BM25 dentro de um único corpus, com a mesma forma de resposta de `GET /api/method/search`
(F3); `GET /api/knowledge/dossier/{id}` devolve necessidade, proposta, implementação e
**desvios**; nenhuma busca do repo A retorna chunk do repo B.

## 4. Corpus: a invariante que não é opção

`corpus_id` particiona **todo** o índice. Não existe busca que misture corpora.

| `corpus_id` | Conteúdo | Quem popula |
| --- | --- | --- |
| `method` | `docs/` do repo blueprint (META, SK, ES, PAT, LS, TS, TP, RI) | `index_method()` |
| `repo:<uuid>` | artefatos, commits, reviews e dúvidas **de um único repo** | `index_artifact()`, `index_commit()`, `index_review()` |

Regras:

1. Toda query SQL do indexador e do retriever carrega `WHERE corpus_id = $1` com o
   corpus **exatamente igual** ao pedido. Não existe `LIKE`, `IN` com dois valores, nem
   "method como fallback" misturado ao repo.
2. `GET /api/knowledge` resolve **um** corpus por requisição: sem `repo` → `method`;
   com `repo=owner/name` → `repo:<uuid>` daquele repo. Para consultar dois corpora, o
   cliente faz **duas** requisições.
3. Uma busca no repo A **nunca** devolve chunk do repo B — nem no método, nem por
   re-rank, nem por fallback de corpus vazio.
4. `index_artifact(doc, corpus_id)` recebe o corpus do chamador e **nunca** deduce o
   corpus por outro caminho.

## 5. Chunking — réplica do `tools/retrieve.py`

Unidade de chunk = **seção H2** (com H1 e H3 como sub-unidades, porque o Blueprint usa
H2 como unidade de decisão). O chunking é uma réplica do `tools/retrieve.py` — mesmo
regex, mesmo corte de 800 caracteres, mesmo tokenize.

```python
_WORD = re.compile(r"\w+", re.UNICODE)
_SPLIT = re.compile(r"^(#{1,3} .+)$", re.M)

def tokenize(text: str) -> list[str]:
    return [w.lower() for w in _WORD.findall(text) if len(w) > 1]
```

Algoritmo de `chunk_markdown(text, heading_path)`:

1. **Remover frontmatter**: se `text` começa com `---`, cortar do segundo `---` em
   diante (idêntico a `tools/retrieve.py`: `text.find("\n---", 3)`).
2. **Dividir** com `_SPLIT.split(text)` — os índices ímpares são headings, os pares são
   corpos.
3. Para cada par (heading, body):
   - `heading = parte.lstrip("# ").strip()`; corpo = a parte seguinte (ou `""`).
   - Se `heading` vazio **ou** `body.strip()` vazio → **pular** o par.
   - `body = body.strip()[:800]` (corte de 800 caracteres, como no `retrieve.py`).
4. **Fallback** (nenhum par sobrevivente): um único chunk com `body = text[:800]`
   (texto já sem frontmatter, **sem** `.strip()` — igual ao `retrieve.py`).
5. `heading` final do chunk:
   - com seção: `" > ".join(heading_path + [heading_da_secao])`;
   - no fallback: `heading_path[-1]` se `heading_path` não for vazia, senão `"documento"`.
6. `token_count = len(tokenize(heading + "\n" + body))`.

`heading_path` é a trilha de ancestrais do chunk (ex.: `["SPEC-024 — Login de alunos"]`).
Ela existe para desambiguar seções homônimas entre documentos: sem ela, `"Contexto"` de
uma SPEC colide com o `"Contexto"` de outra. Para o corpus `method`, `heading_path` é
sempre `[]` — o comportamento é **idêntico** ao `tools/retrieve.py`.

**Invariante de consistência** (verificada por teste): para todo chunk gravado,

```
token_count == len(tokenize(chunk.heading + "\n" + chunk.text))
```

O retriever re-tokeniza o chunk no rerank; se a conta não bater, o score sai errado.

## 6. BM25 em duas etapas

### 6.1 Etapa 1 — candidatos (Postgres FTS)

```sql
WITH q AS (SELECT plainto_tsquery('portuguese', $2) AS tsq)
SELECT c.id, c.artifact_id, c.demand_id, c.source_kind,
       c.heading, c.text, c.token_count, c.corpus_id, c.source_ref
  FROM chunks c, q
 WHERE c.corpus_id = $1
   AND c.tsv @@ q.tsq
 ORDER BY ts_rank_cd(c.tsv, q.tsq) DESC, c.id ASC
 LIMIT 200
```

- Config de stemming: `portuguese` (design master §14.2).
- `plainto_tsquery` — sem operador, sem prefixo: a query é texto livre.
- `ORDER BY … ts_rank_cd DESC, c.id ASC` — o desempate por `id` é **obrigatório**: sem
  ele o `LIMIT 200` é não-determinístico e o conjunto de candidatos (e portanto o
  score) muda entre execuções.
- `$1` é o `corpus_id` exato (§4).

### 6.2 Etapa 2 — rerank em Python puro (stdlib)

Mesma fórmula do `tools/retrieve.py` (`k1=1.5`, `b=0.75`, mesmo tokenize):

```
score(D, Q) = Σ_{t ∈ Q}  idf(t) · (f(t,D) · (k1 + 1)) / ( f(t,D) + k1 · (1 − b + b · dl(D)/avgdl) )

idf(t) = ln( 1 + (N − df(t) + 0.5) / (df(t) + 0.5) )
k1 = 1.5      b = 0.75
f(t,D) = frequência do termo t no chunk D
dl(D) = token_count do chunk D
N     = número de chunks no conjunto de candidatos
df(t) = número de candidatos que contêm t
avgdl = média de token_count dos candidatos
```

Regras do rerank:

- As estatísticas (`N`, `df`, `avgdl`) são calculadas **sobre o conjunto de candidatos**
  (≤ 200 chunks), **não** sobre o corpus inteiro. É o rerank de duas etapas do design
  master §14.2 — não é BM25 sobre o corpus.
- Termo com `df = 0` no conjunto de candidatos → contribui 0 (skip).
- Chunk com score `0` → descartado (`score > 0`), como no `retrieve.py`.
- Desempate final: `score DESC, chunk_id ASC` — determinístico.
- `top` corta a lista final; `top` ∈ [1, 200] (limite do número de candidatos).
- `tokenize(q)` do `retrieve.py`: minúsculas, `\w+`, descarta tokens de 1 caractere.
  **Sem stemming** no Python — o stemming só existe no FTS do Postgres. Termo que o
  Postgres stemma e o Python não (`autenticações` vs `autenticação`) vira candidato e
  some no rerank. É limitação conhecida, medida pelo gold set (§11).
- O `score` devolvido é o BM25 cru, arredondado a 4 casas decimais na serialização.

**Fórmula conferida por teste** — corpus de 2 chunks, D1 = `[a, b, b]` (dl=3), D2 =
`[b, c]` (dl=2), query = `[b]`:

```
idf(b) = ln(1 + (2 − 2 + 0.5)/(2 + 0.5)) = ln(1.2)
avgdl  = (3 + 2)/2 = 2.5
denom(D1) = 2 + 1.5·(1 − 0.75 + 0.75·3/2.5) = 3.725
denom(D2) = 1 + 1.5·(1 − 0.75 + 0.75·2/2.5) = 2.275
score(D1) = ln(1.2) · (2 · 2.5)/3.725 = ln(1.2) · 200/149
score(D2) = ln(1.2) · (1 · 2.5)/2.275 = ln(1.2) · 100/91
```

O teste compara com `math.log(1.2) * 200 / 149` e `math.log(1.2) * 100 / 91`, tolerância
`1e-12`.

### 6.3 Por que BM25 em SQL foi rejeitado

A receita de BM25 em Postgres exige função customizada com `unnest` sobre array de
frequências por documento — mais código, mais superfície de bug, mais difícil de
auditar, e sem ganho mensurável: o corpus é da ordem de 10⁴ chunks. Python puro são
~40 linhas, testáveis sem banco e com a mesma fórmula do `tools/retrieve.py`. Se o
corpus crescer 100×, aí a função em SQL passa a compensar (design master §14.2).

## 7. Migration `005_rag.sql`

`server/migrations/005_rag.sql` — SQL puro, aplicado pelo runner do F1 (ordem
lexicográfica, `schema_migrations`).

```sql
-- 005_rag.sql — F7 (RAG)

-- 1) Chave de idempotência da origem dentro do corpus.
--    source_ref: path relativo a docs/ (corpus 'method') | artifact_id (corpus de repo)
--    | sha do commit | id da review.
ALTER TABLE chunks
    ADD COLUMN IF NOT EXISTS source_ref text NOT NULL DEFAULT '';

-- 2) Reindexar não duplica chunk.
CREATE UNIQUE INDEX IF NOT EXISTS chunks_source_ref_uniq
    ON chunks (corpus_id, source_kind, source_ref)
    WHERE source_ref <> '';

-- 3) tsv preenchida por trigger.
--    Coluna generated seria a alternativa, mas exigiria dropar a coluna tsv criada
--    por F1 (Contrato Comum §4: nunca reescrever tabela). O trigger cobre o mesmo
--    papel sem tocar no DDL canônico.
CREATE OR REPLACE FUNCTION chunks_tsv_update() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    NEW.tsv := to_tsvector('portuguese',
                            coalesce(NEW.heading, '') || ' ' || coalesce(NEW.text, ''));
    RETURN NEW;
END;
$$;

CREATE OR REPLACE TRIGGER chunks_tsv
    BEFORE INSERT OR UPDATE OF heading, text ON chunks
    FOR EACH ROW EXECUTE FUNCTION chunks_tsv_update();

-- 4) Índice do FTS.
CREATE INDEX IF NOT EXISTS chunks_tsv_gin ON chunks USING GIN (tsv);

-- 5) Filtro de corpus (invariante: o corpus nunca cruza corpora).
CREATE INDEX IF NOT EXISTS chunks_corpus_idx ON chunks (corpus_id);

-- 6) Commits reportados podem não chegar ao remoto (design master §13).
--    F4 marca status='orphaned'; o dossiê de F7 os exclui.
ALTER TABLE commits
    ADD COLUMN IF NOT EXISTS status text NOT NULL DEFAULT 'reported';
```

Notas de DDL:

- **Trigger, não coluna generated.** `to_tsvector('portuguese', …)` com `regconfig`
  explícito é `IMMUTABLE` e funcionaria numa generated column (Postgres 12+), mas a
  coluna `tsv` **já existe** no DDL canônico (§8 do design master, criado pela
  migration 001 do F1). Postgres não tem `ALTER … SET GENERATED`; só existe
  `DROP COLUMN` + `ADD COLUMN`, ou seja, reescrever a tabela — proibido pelo Contrato
  Comum §4. O trigger tem o mesmo efeito (tsv sempre coerente com `heading` + `text`),
  é idempotente (`CREATE OR REPLACE`, Postgres 14+) e não toca no DDL do F1.
- O índice GIN pode já existir se o F1 criou conforme §8.1 do design master. Verificar
  `SELECT indexname FROM pg_indexes WHERE tablename = 'chunks'` antes de criar: o
  `IF NOT EXISTS` só protege contra o **mesmo nome**, e um segundo índice GIN
  equivalente é desperdício, não erro.
- `source_ref` é `NOT NULL DEFAULT ''` — o default evita reescrita de tabela e o índice
  parcial (`WHERE source_ref <> ''`) ignora as linhas legadas.
- `corpus_meta` **não existe**: o DDL do design master §8 é fechado e **nenhuma tabela
  nova** é criada por esta fase (F6 D5 segue a mesma regra). O hash do corpus `method`
  é persistido como **evento** em `events.payload` — mesmo mecanismo de publicação que
  o F6 usa (`events` é append-only e é o canal de estado sem DDL novo). Ver §8.3.
- `commits.status` é coluna nova (`reported` | `orphaned`), additive. **Coordenação com
  F4:** `POST /api/demands/{id}/reconcile` (design master §13) é do F4 e deve marcar
  `status='orphaned'`; até o F4 marcar, o dossiê não exclui nada (comportamento seguro,
  sem crash). O valor default `'reported'` garante que commits já gravados não somem.

## 8. Indexação

### 8.1 Regras comuns

| Regra | Detalhe |
| --- | --- |
| Dedup | Antes de inserir, apaga o que vai ser reinserido: `DELETE FROM chunks WHERE corpus_id = $1 AND source_ref = $2` (artefato, commit, review). O corpus `method` é apagado **inteiro** quando o hash muda (§8.3). O índice único `chunks_source_ref_uniq` garante que não haja duplicata mesmo com concorrência. |
| `source_kind` | `'method' \| 'br' \| 'spec' \| 'commit' \| 'review' \| 'doubt'` (DDL §8). |
| `source_kind` de artefato | Por **path** (canônico, META-004), com o `kind` do `ArtifactDoc` como segundo critério: `docs/BR/…` → `br`; `docs/SPEC/…` → `spec`; `docs/implementation-artifacts/duvidas-*` → `doubt`; senão, `kind == "br"` → `br`, `kind == "spec"` → `spec`; senão **não indexa** (retorna 0). |
| `source_ref` | `method` → path relativo a `docs/` (posix, ex.: `ES/ES-007_OUTPUT_PORT_MODEL.md`); artefato → `artifact_id`; commit → `sha`; review → `review.id`. |
| `artifact_id` de artefato | Resolver por `(repo_id, path)` na tabela `artifacts`; se não achar, usar o `id` do frontmatter (`BR-013` / `SPEC-024`). Se não resolver **nenhum dos dois** → não indexar (retorna 0): chunk sem `artifact_id` num corpus de repo duplicaria a cada sync. |
| `demand_id` de artefato | Vem da linha de `artifacts` (`artifacts.demand_id`). Sem linha de `artifacts` → `NULL`. |
| `corpus_id` de artefato | É o parâmetro `corpus_id` recebido — nunca deduzido. |
| `corpus_id` de commit | `f"repo:{commit.repo_id}"`. |
| `corpus_id` de review | `f"repo:{repo_id}"`, com `repo_id` vindo de `SELECT repo_id FROM commits WHERE id = $1` (a tabela `reviews` não tem `repo_id`). Commit ausente → retorna 0. |
| `token_count` | `len(tokenize(heading + "\n" + text))` do chunk final (§5, passo 6). |
| Transação | Cada chamada de indexação roda em uma transação: delete + inserts (+ evento, no caso do corpus `method`). Índice nunca fica pela metade. |

### 8.2 `chunk_markdown(text, heading_path) -> list[Chunk]`

Sincrono, puro, sem banco — é o mesmo contrato do `tools/retrieve.py` (§5 desta spec).
`Chunk` (definido por F7 em `services/indexer.py`):

```python
@dataclass
class Chunk:
    heading: str
    text: str
    source_kind: str
    artifact_id: str | None = None
    demand_id: str | None = None
    corpus_id: str = "method"
    token_count: int = 0
```

### 8.3 `async def index_method() -> int`

1. `root = settings.repo_root / "docs"`; `files = sorted(root.rglob("*.md"))`.
2. `content_hash` do corpus = sha256 da concatenação (ordem alfabética) de
   `f"{relpath}:{sha256(conteudo)}\n"` → hexdigest.
3. Hash persistido = último evento de indexação:

```sql
SELECT payload->>'content_hash' AS content_hash
  FROM events
 WHERE type = 'method_corpus_indexed'
 ORDER BY id DESC
 LIMIT 1;
```

   Sem evento (primeira vez) → hash persistido é `NULL` → reindexa.
   Se `content_hash` persistido == o hash atual → **retorna 0** (nada mudou).
4. Senão, em uma transação: `DELETE FROM chunks WHERE corpus_id = 'method'`; para cada
   arquivo, `chunk_markdown(conteudo, heading_path=[])` → inserts com
   `source_kind='method'`, `artifact_id=NULL`, `demand_id=NULL`, `corpus_id='method'`,
   `source_ref=relpath`; e **um evento**:

```sql
INSERT INTO events (demand_id, artifact_id, type, payload, actor)
VALUES (NULL, NULL, 'method_corpus_indexed',
        $1::jsonb, NULL);
-- $1 = {"content_hash": "<hex>", "chunk_count": <n>, "root": "docs"}
```

5. Retorna o **número de chunks inseridos**.

Leitura do disco é só leitura (design master §7.1, invariante 4). O hash **não** vira
tabela nova (§7, notas de DDL).

### 8.4 `async def index_artifact(doc: ArtifactDoc, corpus_id: str) -> int`

1. `source_kind = source_kind_for(doc.path, doc.kind)`; `None` → retorna 0.
2. Resolver `artifact_id` / `demand_id` (§8.1); sem `artifact_id` → retorna 0.
3. `heading_path` = `[f"{id} — {title}"]` a partir do frontmatter (`id`, `title`),
   descartando partes vazias; `[]` se o frontmatter não tiver nenhum dos dois.
4. `chunks = chunk_markdown(doc.content, heading_path)`.
5. Transação: delete por `(corpus_id, source_ref)` + inserts.
6. Retorna o número de chunks inseridos.

### 8.5 `async def index_commit(commit: Commit) -> int`

1. `corpus_id = f"repo:{commit.repo_id}"`; `source_ref = commit.sha`;
   `source_kind = 'commit'`; `demand_id = commit.demand_id`; `artifact_id = NULL`.
2. `text = commit.message + "\n\n" + "\n".join(commit.files or [])`.
3. `heading_path = [f"commit {commit.sha[:7]}"]` → o chunk fallback sai com
   `heading = "commit 9f3a1c2"`.
4. Transação: delete por `(corpus_id, source_ref)` + inserts. Retorna a contagem.

### 8.6 `async def index_review(review: Review) -> int`

1. `repo_id` via `SELECT repo_id FROM commits WHERE id = $1`; ausente → retorna 0.
2. `corpus_id = f"repo:{repo_id}"`; `source_ref = review.id`; `source_kind = 'review'`;
   `demand_id = review.demand_id`; `artifact_id = NULL`.
3. **Um chunk por finding**, montando um markdown sintético para reusar o mesmo
   chunker (cada finding vira uma seção `## `):

```markdown
## AC-003 — Título do achado

detalhe do achado

sugestão do revisor
```

   Um review sem findings vira **um** chunk com o resumo
   (`verdict: clean` / `verdict: blocking`).
4. `heading_path = [f"review {commit_sha[:7]} — {verdict}"]`.
5. Transação: delete por `(corpus_id, source_ref)` + inserts. Retorna a contagem.

### 8.7 Quando a indexação roda

F7 **não edita `main.py`** (F1). A indexação do corpus do método é disparada pelo
próprio `search()`:

- `ensure_method_indexed()` — calcula o hash do corpus; se mudou, chama
  `index_method()`. Cache em processo de **60 s** (TTL) para não reler `docs/` a cada
  busca.
- Indexação de repo acontece quando o repo sincroniza (`POST /api/artifacts/sync`, F4) e
  quando commits/reviews são reportados (F4/F6 chamam `index_artifact` / `index_commit` /
  `index_review` por import tardio dentro do handler — o mesmo padrão do Contrato Comum
  §8.1 para o pipeline de aprovação).
- F1 **pode** chamar `await indexer.index_method()` no startup (import tardio). F7 não
  depende disso: se F1 não chamar, `ensure_method_indexed()` cobre.

## 9. Rotas — `server/app/routers/knowledge.py`

F7 é dona de `app/routers/knowledge.py`. O prefixo `/api` é aplicado pelo F1 em
`main.py`; as rotas abaixo são relativas a ele.

### 9.1 `GET /api/knowledge?q=&repo=&top=`

| Parâmetro | Tipo | Regra |
| --- | --- | --- |
| `q` | string | **obrigatório**, `min_length=1`. Ausente → 422 (schema). |
| `repo` | string | opcional, padrão `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$` → não casa → 422. Vazio/ausente → corpus `method`. |
| `top` | int | padrão `10`, `ge=1`, `le=200`. Fora → 422. |

Fluxo:

1. `require_user` (Contrato Comum §6) — 401 sem sessão/token.
2. Se `repo` vier: resolver `repos` por `(owner, name)` → inexistente → **404**
   `{"error":{"code":"repo_not_found","message":"repo não registrado"}}`.
   Se o chamador é um token de outro repo (`await current_repo(request)` devolve
   `"owner/name"` diferente do pedido) → **403**
   `{"error":{"code":"repo_forbidden","message":"token sem acesso ao repo"}}`.
   Sessão web (cookie) não tem restrição de repo.
3. `corpus_id = "method"` ou `f"repo:{uuid}"`.
4. `hits = await search(q, corpus_id, top)`.
5. Responder 200 com o corpo da §9.2.

### 9.2 Contrato de resposta (F3 ↔ F7) — **não muda**

`GET /api/knowledge` (F7) e `GET /api/method/search` (F3) devolvem **a mesma forma**:

```json
{
  "query": "quando criar um Output Port",
  "hits": [
    {
      "heading": "Section: Hinge — When to Create an Output Port",
      "text": "Um Output Port é criado quando…",
      "score": 4.1823,
      "source_kind": "method",
      "artifact_id": null,
      "demand_id": null,
      "corpus_id": "method"
    }
  ]
}
```

Regras do contrato:

- **Chaves do topo**: exatamente `query` e `hits`.
- **Chaves de cada hit**: exatamente `heading`, `text`, `score`, `source_kind`,
  `artifact_id`, `demand_id`, `corpus_id` — **nenhuma a mais, nenhuma a menos**.
  `chunk_id` **não** é serializado (é interno do servidor; o cliente não precisa dele e a
  forma tem que ser idêntica entre F3 e F7).
- F3 entrega essa forma de forma **provisória** (FTS puro, `score` = `ts_rank_cd`);
  F7 sobe para BM25 de duas etapas **sem mudar a forma**. A escala do `score` muda
  (BM25 não é limitado a 1) — o cliente usa o score só para ordenar.
- `hits` vem ordenado por `score DESC, chunk_id ASC`. `hits` vazio é 200 com `[]` (não
  404).

### 9.3 `GET /api/knowledge/dossier/{demand_id}`

- `demand_id` = `uuid.UUID` no path → malformado → 422.
- `require_user` → 401; token de outro repo → 403 (mesma regra da §9.1, com o repo da
  demanda).
- Demanda inexistente → **404** `{"error":{"code":"demand_not_found","message":"demanda inexistente"}}`.
- Corpo: §10.

### 10.2 Regras de montagem

| Parte | Regra |
| --- | --- |
| `necessidade.br` | Artefatos da demanda com `kind = 'br'` (tabela `artifacts`), ordenados por `id`. |
| `necessidade.acs` | ACs do **corpo da BR**, extraídas com o mesmo regex do linter (F2 `BR-004`): `\bAC-\d{3}\b`. O `title` é o resto da linha da primeira ocorrência: regex `^\s*(?:[-*]\s*)?(?:\*\*)?(AC-\d{3})(?:\*\*)?\s*[:.\-–—]?\s*(.*)$` → grupo 2, `""` se vazio. Ordenadas por id. |
| `proposta.specs` | Artefatos da demanda com `kind = 'spec'`, ordenados por `id`. |
| `proposta.grafo` | Linhas de `spec_edges` em que `parent_id` e `child_id` são SPECs da demanda; `type` ∈ `depends_on \| derives_from \| tests`. |
| `implementacao.commits` | `commits` da demanda, **excluindo `status = 'orphaned'`** (design master §13), ordenados por `created_at ASC, sha ASC`. |
| `implementacao.reviews` | `reviews` da demanda, ordenados por `created_at ASC, id ASC` (a rota `GET /api/reviews?demand=` do F6 devolve em ordem inversa — o dossiê é uma linha do tempo, então ordena na montagem); `commit_sha` vem de `commits.sha` (join). |
| `necessidade.acs[].specs` | SPECs da demanda cujo corpo cobre a AC. Cobertura de SPEC = ACs na seção **"Acceptance Criteria atendidos"** (heading normalizado como F2 §5.2) **ou** no frontmatter `acceptanceCriteria`; se a SPEC não tiver nem um nem outro, usa o corpo inteiro. |
| `necessidade.acs[].commits` | `sha[:7]` dos commits da demanda que referenciam a AC: o `message` do commit contém `AC-\d{3}` **ou** o commit toca (`files`) o `path` de uma SPEC que cobre a AC. |

### 10.3 Regras de `desvios`

Toda entrada de `desvios` tem `kind`, `ac` (string ou `null`), `title` e `detail`.

| `kind` | Quando entra | Campos extras |
| --- | --- | --- |
| `ac_sem_spec` | AC da BR que **nenhuma** SPEC da demanda cobre. | `specs: []` |
| `ac_sem_commit` | AC coberta por ≥1 SPEC, mas **nenhum** commit da demanda a referencia. | `specs: [...]` |
| `finding_bloqueante` | Finding de review com `severity = "blocking"` cuja dúvida correspondente **não** está `cleaned`. | `artifact_id`, `commit_sha`, `severity`, `suggestion`, `doubt_status` |

Regra de "não tratado" (finding_bloqueante): a tabela `doubts` (F6) **não tem coluna
`ac`** — o AC fica dentro do texto da `question`, no formato canônico do F6 (§5.5 do
F6): `"[<ac>] <title> — <detail>"`. O finding está aberto quando existe uma linha em
`doubts` com:

```sql
SELECT 1
  FROM doubts
 WHERE artifact_id = $1          -- artefato revisado (SPEC ou BR)
   AND source = 'reviewer'       -- dúvida vinda do revisor, não do linter
   AND status <> 'cleaned'        -- 'pending' e 'deferred' contam como aberto
   AND question LIKE $2           -- '[AC-003]%'  (ou '[]%' quando ac == "")
 LIMIT 1;
```

- `$2` = `'[' || <ac do finding> || ']%'`. Achado de estrutura (sem AC específica) tem
  `ac == ""` (F6 §5.3) → prefixo `'[]%'`.
- `status <> 'cleaned'` — `pending` e `deferred` contam como aberto (F6 §5.7: só
  `cleaned` libera a aprovação).
- Se não houver linha correspondente, o finding é considerado **tratado** (não entra no
  dossiê) — revisão antiga sem pendência não vira desvio eterno.

Ordem de `desvios`: `ac_sem_spec`, `ac_sem_commit`, `finding_bloqueante`; dentro de
cada grupo, por id de AC; findings por `commit_sha` e título.

## 11. Upgrade path: embeddings só se o recall medido falhar

**Regra (design master §14.3):** embeddings entram **só** se o recall medido falhar.
Claude API **não tem endpoint de embeddings** — as opções seria Voyage (pago) ou modelo
local. Nenhuma das duas entra em F7 (YAGNI, design master §5).

O gate:

| Item | Valor |
| --- | --- |
| Gold set | `server/tests/gold_set.json` — **20 casos**, formato abaixo. |
| Métrica | `recall@5` = fração de casos em que o chunk esperado está entre os 5 primeiros hits do `search()` final. |
| Limiar | **≥ 0.80** (16 de 20 casos). Abaixo disso, a mudança no indexador **não é aceita**. |
| Quando medir | A cada mudança de chunking, tokenize, corpus ou migration do índice. O número vai no corpo do PR. |
| Se falhar | Primeiro corrigir o lexical (chunking, tokenize, stemming, corpus). Só depois de esgotar o lexical, abrir uma spec nova para embeddings (Voyage ou modelo local) — **fora de F7**. |

Formato do gold set (`server/tests/gold_set.json`):

```json
{
  "version": 1,
  "cases": [
    {
      "q": "quando criar um Output Port",
      "corpus_id": "method",
      "expect_ref": "ES/ES-007_OUTPUT_PORT_MODEL.md",
      "expect_heading": "Section: Hinge — When to Create an Output Port"
    }
  ]
}
```

- `expect_ref` = `source_ref` do chunk esperado (path relativo a `docs/` para o corpus
  `method`).
- `expect_heading` = `heading` exato do chunk esperado.
- O caso conta como acerto se **existe** um hit no top-5 com o mesmo `(source_ref,
  heading)` — o `chunk_id` é uuid e muda a cada reindexação, por isso o gold set
  identifica o chunk por origem, não por id.
- Os 20 casos são sobre o corpus `method` (o corpus de repo não tem corpus estável
  entre execuções — testes de repo usam fixtures próprios).

## 13. Critérios de aceitação

- [ ] `GET /api/knowledge?q=…` devolve **exatamente** `{"query", "hits"}` e cada hit
      **exatamente** as 7 chaves do contrato (§9.2).
- [ ] A forma de `GET /api/knowledge` é idêntica à de `GET /api/method/search` (F3) —
      teste comparando o conjunto de chaves (marcado `skip` se F3 estiver pendente).
- [ ] `chunk_markdown` reproduz `tools/retrieve.py`: mesmo regex `^(#{1,3} .+)$`, mesmo
      corte de 800 chars, mesmo tokenize, frontmatter removido, parágrafo sem body
      pulado, fallback em texto sem heading.
- [ ] `token_count` gravado == `len(tokenize(heading + "\n" + text))` para todo chunk.
- [ ] O score BM25 bate com `ln(1.2)·200/149` e `ln(1.2)·100/91` no caso de teste da
      §6.2 (tolerância `1e-12`).
- [ ] A busca no repo A **nunca** devolve chunk do repo B (teste com dois repos
      indexados).
- [ ] `index_artifact` duas vezes no mesmo artefato → **mesmo** número de chunks
      (sem duplicata).
- [ ] `index_method` duas vezes → a segunda retorna **0** (hash igual) e a contagem de
      chunks em `chunks` não muda.
- [ ] `tsv` preenchida em todo insert/update (trigger) e o índice GIN existe.
- [ ] `GET /api/knowledge/dossier/{id}` devolve as 4 chaves de topo e a `desvios`
      detecta: AC sem SPEC, AC sem commit e finding bloqueante aberto.
- [ ] Commit `orphaned` não aparece em `implementacao.commits`.
- [ ] `recall@5` do gold set ≥ 0.80.
- [ ] `tools/retrieve.py` **inalterado** (`git diff --stat tools/` vazio).
- [ ] `pytest server/tests` verde.
